SAP CPI Encryption and Decryption in a Simple Flow (Using Postman)

Why Encrypt Messages in an Integration Flow?

Most connections in CPI already use HTTPS, which encrypts the data while it travels between two systems. That is called transport-level security. But a message does not always stay inside one connection. It can be written to a file, dropped on an SFTP server, sent by email or handled by several systems before it reaches the final receiver. In those cases you can protect the message itself. That is message-level security, and it is what the Encryptor and Decryptor steps in CPI are for.

Typical examples are payroll or bank files sent to external providers, and messages that must stay unreadable for everyone except the intended partner.

How a "Digital Envelope" Works

Encrypting a large message directly with a public key would be slow. So the PKCS #7 / CMS standard (called enveloped data) uses two kinds of keys together:

  1. The content is encrypted with a fast symmetric key that is created on the fly.
  2. That symmetric key is encrypted with the receiver's public key and stored inside the message.
  3. Only the owner of the matching private key can unlock the symmetric key, and then the content.

The rule to remember: public key encrypts, private key decrypts. The sender needs only the receiver's public key (a certificate). The private key never leaves the receiver.

In this article we use PKCS7/CMS Enveloped Data, because you can create the key pair directly in the CPI keystore and you do not need any extra tools. OpenPGP is widely used with banks and payroll vendors, but it needs separately prepared PGP key rings.

What You Will Build

You build two small flows, and test them with Postman:

  • Encrypt flow at /encrypt: plain text in, encrypted and Base64-encoded text out.
  • Decrypt flow at /decrypt: that Base64 text in, original plain text out.

This article continues from article 3. You need the same service instance and service key for Postman, and you should already know how to create a flow with an HTTPS sender, deploy it and call it from Postman.

Use made-up text only

In this practice setup the same tenant can encrypt and decrypt. Never use real employee, salary or customer data for learning. Use harmless sample text.

Step 1: Create a Key Pair in the Keystore

  1. Open Monitor → Integrations and APIs and choose the Keystore tile under Manage Security.
  2. Choose Create → Key Pair.
  3. Enter an Alias, for example sapwithsai_demo, and a Common Name (CN), for example sapwithsai-demo.
  4. Choose the key type RSA and a key size of at least 2048 bits, set a validity period, and choose Create.

You now have one key pair with a public part (the certificate) and a private part. The alias is the name that the Encryptor and Decryptor steps use to find them.

Why one key pair here, and two in real life

In this demo one key pair plays both roles, like writing a letter to yourself. In a real scenario the receiving partner creates the key pair and sends you only the certificate. You import it into your keystore and use it to encrypt. The partner keeps the private key and uses it to decrypt.

The keystore is shared

All integration flows on the tenant use the same keystore. Give your demo key a unique alias and never delete or overwrite entries you did not create, because other flows may depend on them.

Step 2: Build the Encrypt Flow

  1. In your package add a new integration flow, for example Encrypt_Message_Demo, and choose Edit.
  2. Delete the Receiver. Draw a line from the Sender to the Start event and choose the HTTPS adapter, as in article 3.
  3. Set Address to /encrypt, keep User Role ESBMessaging.send and untick CSRF Protected for this practice flow.
  4. In the palette choose Security Elements → Encryptor → PKCS7/CMS Enveloped Data and drop it on the line between Start and End.
  5. In the Encryptor properties, on the Processing tab, set:
    • Content Encryption Algorithm: an AES option, for example AES/CBC/PKCS5Padding.
    • Secret Key Length: the longest value offered for your algorithm, for example 256 bits. The available lengths depend on the algorithm you pick.
    • Receiver Public Key Alias: choose Add and enter your alias, sapwithsai_demo.
  6. Add an Encoder → Base64 Encode step after the Encryptor.
  7. Save and Deploy.

Why the Base64 step? The encrypted result is binary data. Postman and other text tools cannot display binary data properly. Base64 converts the binary data into plain text that you can copy and paste safely.

Step 3: Build the Decrypt Flow

  1. Add another integration flow, for example Decrypt_Message_Demo, and choose Edit.
  2. Delete the Receiver and connect the Sender to Start with an HTTPS adapter. Set Address to /decrypt and, as before, role ESBMessaging.send and CSRF Protected off.
  3. Add a Decoder → Base64 Decode step first. It turns the pasted text back into binary data.
  4. After it add Security Elements → Decryptor → PKCS7/CMS Enveloped Data.
  5. In the Decryptor properties enter the Private Key Alias: the same alias, sapwithsai_demo.
  6. Save and Deploy.

The order matters. When you encrypt you go Encrypt → Base64 Encode. When you decrypt you must reverse it: Base64 Decode → Decrypt.

Step 4: Test Both Flows in Postman

  1. Open Manage Integration Content and copy the endpoints of both flows. They end with /http/encrypt and /http/decrypt.
  2. Create a Postman request POST to the /encrypt endpoint. Use the same OAuth 2.0 Client Credentials setup as in article 3.
  3. In the body choose raw → Text and enter harmless text, for example: 
    Hello SAPwithSAI - this is a secret test message
  4. Choose Send. The response is a long Base64 text. It is unreadable on purpose. Copy the whole response without extra spaces.
  5. Create a second POST request to the /decrypt endpoint with the same authorization.
  6. Paste the Base64 text into the body (raw → Text) and choose Send.

The response of the second call should be exactly your original text. You have just encrypted and decrypted a message inside CPI.

Experiments that teach you a lot

  • Change one character in the Base64 text and call /decrypt again. Decryption should fail, because the message was altered.
  • Encrypt the same text twice. The two Base64 results differ, because a new symmetric key is generated each time, yet both decrypt to the same text.
  • Remove the Base64 Decode step from the decrypt flow, redeploy and test. See which error you get, then restore it.

How This Looks in a Real Project

  • Outbound: your flow builds a file or message, the Encryptor uses the partner's public certificate from your keystore, and the result is sent by SFTP or another channel.
  • Inbound: a partner encrypts with your public certificate. Your flow decrypts with your private key, which stays in the keystore.
  • Integrity and origin: encryption keeps a message secret. To prove who sent it and that nobody altered it, add a Signer and, on the other side, a Verifier.
  • Certificate expiry: certificates expire. Note the validity dates in the Keystore and plan the renewal with your partner before they end.
  • Never expose a decrypt endpoint openly. The demo endpoint exists only to teach. In production, decryption happens inside a protected flow that processes the result, not behind an open URL.
  • Sensitive data and logs: do not use Debug or Trace log levels with real personal data, because they can show message content.

Interview Questions

1. What is the difference between encryption and signing?

Encryption keeps the content secret so only the intended receiver can read it. Signing proves who sent the message and that it was not changed. They solve different problems and are often used together.

2. Which key encrypts and which key decrypts?

The receiver's public key encrypts. The receiver's private key decrypts. The private key never leaves the receiver.

3. Why do we use Base64 after the Encryptor?

Encrypted output is binary. Base64 converts it into text so that it can be displayed, copied and transported safely through text-based channels. The receiver must Base64-decode it before decrypting.

4. What is the difference between PKCS7/CMS and OpenPGP in CPI?

Both encrypt messages. PKCS7/CMS uses X.509 certificates and key pairs from the tenant keystore. OpenPGP uses PGP key rings that are deployed as security material, and is common with banks and payroll providers.

5. Where are keys and certificates stored in CPI?

Key pairs and certificates are stored in the tenant keystore (Monitor, Manage Security, Keystore). Credentials and PGP key rings are deployed as security material.

Frequently Asked Questions

Can I encrypt a file instead of a text message?

Yes. The Encryptor works on the message body, so a file read by an SFTP adapter or a payload built in the flow can be encrypted in the same way.

Do I need an extra tool to create the key?

Not for PKCS7/CMS. You can create the key pair directly in the CPI keystore, as in this article. OpenPGP needs key rings prepared with a PGP tool.

What happens if the certificate expires?

Encryption or decryption with that key can fail. Replace the certificate before it expires and coordinate the change with your partner.

Conclusion

You built two small flows that encrypt and decrypt a message with PKCS7/CMS, and tested them with Postman. You learned why Base64 is needed, how the keystore alias connects the steps, and how the same pattern appears in real projects with partners. From here you can move on to signing and verifying messages, to OpenPGP, and to mappings and error handling in larger flows.
